# ReFlow — Razorpay AI Buildathon Brief

> Research-phase document. Last verified: 2026-08-29.

Razorpay AI Buildathon 2026 is a student-only hiring challenge for AI Builder Interns. The public submission must show a working build, a public repository, a roughly five-minute pitch video, and the architecture. The internship offer advertised by Razorpay is 6 or 12 months, in person in Bangalore, from September, with a ₹75,000 monthly stipend.

Official page: https://razorpay.com/buildathon/

## Selected track

**Track 04 — AI Finance Controller**

Razorpay's wording is unusually specific:

- close **one finance-operations loop**;
- evaluate it across a **50+ record batch of synthetic data**;
- report **match rate**;
- report **exceptions the system could not resolve**;
- show **throughput**;
- show **measured accuracy**;
- give an **honest exception list** rather than cherry-picking a successful match.

The chosen loop is **end-to-end settlement reconciliation**:

`merchant order ledger → payment/refund events → Razorpay settlement-recon ledger → settlement batch → bank credit → exception investigation → resolution/review`

## Product thesis

**ReFlow is an evidence-first reconciliation controller that can account for every rupee in a settlement and investigate what does not reconcile.**

Most demo reconciliation systems reduce the problem to one gateway row matching one bank row. That is not the interesting part of payment reconciliation. Razorpay's own settlement-recon API shows that a settlement can contain payments, refunds, transfers and adjustments, each with credits/debits, fees, taxes, timestamps and settlement IDs. The bank then exposes a settlement-level credit identified by a UTR.

ReFlow therefore treats reconciliation as a **many-to-one temporal evidence graph**, not a fuzzy string-match problem.

## Non-negotiable design principles

1. **Deterministic code owns financial truth.** An LLM never calculates balances, decides whether money moved, changes a match, or silently repairs a ledger.
2. **AI performs investigation, not arithmetic.** It selects safe read-only investigation tools, gathers the relevant evidence, explains discrepancies, proposes bounded resolutions, and knows when to escalate.
3. **Exceptions are a correct output.** Uncertainty must fail closed into a typed exception; it must never be converted into a confident-looking match.
4. **Every result is reproducible.** Synthetic data generation is seeded. Ground truth is held outside the reconciliation pipeline. The same corpus is used for all compared strategies.
5. **Every rupee must have provenance.** Reconciled amounts must be traceable to source records and arithmetic identities.
6. **Event semantics are first-class.** Webhook duplicates, out-of-order delivery and late state changes are expected conditions, not edge cases bolted on at the end.
7. **No benchmark theatre.** Report false auto-match rate, unresolved rate, residual amount, latency/throughput and failure slices, not one flattering headline accuracy number.

## Winning bar we are setting for ourselves

The official minimum is 50+ records. ReFlow should exceed that significantly while keeping the demo understandable.

Target benchmark:

- 1,000+ transaction-level synthetic records;
- multiple settlement batches;
- payments, refunds and adjustments at minimum;
- bank-side settlement credits;
- 12+ adversarial anomaly families;
- deterministic held-out ground truth;
- transaction attribution precision/recall;
- settlement-balance accuracy;
- exception classification precision/recall;
- **silent false-match rate** as a first-class metric;
- unexplained residual amount in paise;
- p50/p95 batch latency and records/sec;
- agent tool-selection/faithfulness eval on a held-out exception set;
- explicit unresolved cases and limitations.

We do not set target result numbers in advance. Results will be measured after implementation.

## What ReFlow is not

ReFlow is not:

- a generic finance chatbot;
- a PDF/CSV summarizer;
- an LLM that guesses whether rows match;
- a tax-compliance product pretending to know every merchant's legal context;
- a clone of Razorpay's existing Intelligent Reconciliation interface;
- a revenue-recovery submission with a different name;
- an accounting system of record.

It is a narrow, testable finance-control loop with explicit evidence and measurable correctness.

## Submission rule

No README claim may be promoted to a headline result until it is generated by a checked-in reproducible evaluation command. If a result changes after a bug fix, the old claim is removed and the failure is documented rather than hidden.
